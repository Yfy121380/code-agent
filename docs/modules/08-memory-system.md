# 记忆系统模块笔记

## 1. 模块定位

记忆系统负责让 Codemate 在长任务和跨会话使用中保持连续性。它解决的不是“把所有历史都永久保存下来”，而是把不同生命周期的信息分开管理：当前任务需要立即用到的信息进入工作记忆，跨会话仍然稳定有用的信息进入长期记忆。

Codemate 的记忆分为两层：

- **工作记忆**：session 内的短期状态，服务当前任务和当前上下文组装。
- **长期记忆**：项目级跨会话信息，服务未来会话的偏好、工作方式和项目背景恢复。

这两层的边界非常重要。工作记忆强调“当前任务相关”和“滚动更新”，可以频繁变化；长期记忆强调“稳定、有复用价值”，不能把临时调试过程、当前 todo、一次性工具输出都塞进去。

## 2. 整体设计

记忆系统的核心思路是：不要让模型在越来越长的 history 里反复寻找关键信息，而是把有价值的信息沉淀到更稳定、更短的结构中。

整体流程可以概括为：

```text
用户请求开始
  -> 更新当前任务摘要
  -> 过期旧过程笔记
  -> 召回相关长期记忆
  -> 组装 prompt

工具执行完成
  -> 读/写文件更新工作记忆
  -> 工具失败记录过程笔记
  -> 工具成功清理相关过程笔记

最终回答前
  -> 如果有跨会话值得记住的信息，追加 daily log

后台 dream
  -> 读取未整理 daily logs
  -> 整理成三类长期记忆文件
```

这样设计后，history 仍然保存完整对话和工具观察，但不再承担所有状态恢复职责。即使旧 history 被 compact，工作记忆和长期记忆仍然能保留当前任务和跨会话的重要信息。

## 3. 工作记忆

工作记忆是当前 session 的短期状态，会随工具调用和用户请求滚动更新。它不是长期知识库，也不做关键词召回，而是在每次 prompt 组装时全部展示在 `Working memory` 中。

工作记忆主要包含：

- 当前任务摘要。
- 最近访问文件。
- 文件摘要。
- 过程笔记。
- 当前 todo。
- active skills。
- runtime context。

其中前四项属于 memory state；todo 和 active skills 也展示在 Working memory，因为它们同样服务当前任务执行。

### 当前任务摘要

每次用户发起请求时，Codemate 会把本轮用户请求写入任务摘要。它的作用是让模型在多轮工具调用中始终知道“当前正在完成什么”。

任务摘要不是最终答案，也不是完整需求文档。它只是一条短状态，用来降低长工具链中目标漂移的概率。比如模型连续读了很多文件后，仍然能从工作记忆中看到当前任务是什么。

### 最近访问文件

最近访问文件记录 agent 最近读写过哪些文件。它主要解决两个问题：

- 帮助模型快速回忆刚才处理过的文件。
- 支持编辑前 freshness 校验，避免没有读过文件就直接改。

最近文件会做数量限制，目前只保留最近 12 个。这个限制是必要的，因为“最近访问”越旧越不可靠，而且过多文件名会让工作记忆变成另一个 history。

路径会被规范化：

- workspace 内文件用相对路径展示，便于阅读。
- workspace 外文件用真实绝对路径保存，避免不同写法指向同一文件时无法校验。

### 文件摘要

文件摘要是 `read_file` 成功后的轻量摘要。它不会保存完整文件内容，而是把读取结果中前几行非空内容压缩成短文本。

文件摘要的职责是让模型快速想起“这个文件大概是什么”，而不是替代原始工具结果。原始内容仍在 history 中；摘要只作为短期提示。

这里要注意一个边界：文件摘要和长期记忆不是一回事。文件摘要是当前 session 的工作状态，文件变化后会失效；长期记忆是跨会话稳定信息，不应该保存大段文件内容。

### Freshness 校验

文件摘要会保存 freshness，也就是文件内容哈希。每次渲染工作记忆或检查是否允许编辑时，都会判断摘要对应的文件是否还是同一个内容版本。

这个设计解决的是“读过文件”和“读过且仍然可信”的区别：

- 如果文件没变，摘要可以继续作为轻量上下文。
- 如果文件被修改，旧摘要会被视为过期，不再展示。
- `write_file` 和 `patch_file` 成功后，会主动让对应文件摘要失效。

因此模型不会在修改文件后继续依赖旧摘要。

### 过程笔记

过程笔记记录工具异常调用，用来提醒模型不要重复犯同样的错误。它主要包含：

- `invalid_arguments`：工具参数不合法。
- `repeated_call`：重复相同工具调用被拦截。
- `approval_denied`：用户拒绝审批。
- `rejected`：工具或权限策略拒绝。
- `error`：工具执行失败。

过程笔记记录的是“调用行为问题”，不是业务知识。它的价值在于后续几轮 prompt 中提醒模型：这个调用失败过，需要换参数、换路径、换工具或停止重复尝试。

过程笔记会保存工具名、错误类型、参数摘要、错误信息、出现次数和 turn 信息。参数摘要会截断，避免把大段内容写进工作记忆。

### 过程笔记清理

过程笔记必须及时清理，否则会长期污染当前任务。当前有两类清理策略：

- **TTL 清理**：超过若干 turn 后自动删除。
- **成功清理**：工具成功后删除已解决的相关笔记。

具体规则是：

- `repeated_call` 在任意成功工具调用后清理。
- `invalid_arguments`、`approval_denied`、`rejected`、`error` 在同工具成功后清理。

这样可以避免两种问题：模型不断重复错误调用；错误已经解决后，旧提醒还继续误导模型。

### Current Todos

Todo 计划也展示在 Working memory 中，格式是阶段式计划：

```text
current_todos: follow these phases and tasks until completed
1. [in_progress] 分析权限系统调用链
   - [completed] 定位工具注册入口
   - [in_progress] 梳理 run_shell 校验流程
2. [pending] 汇总问题并给出修改建议
```

它放在工作记忆中，是因为 todo 表示当前任务的执行计划，不是长期事实，也不是普通 history。模型每轮都能看到未完成计划，从而继续跟随计划执行。

如果所有 todo 都完成，系统会清空 todo，避免已完成计划继续占用上下文。

### Active Skills

已加载 skill 也进入 Working memory。它包含 skill 名称、skill root 和 `SKILL.md` 指令内容。

这样设计是为了让 skill 能跨多轮任务持续生效。复杂任务通常不是一轮工具调用就结束，如果 skill 只作为一次工具结果存在，很容易随着 history 增长而淡出上下文。放在 Working memory 后，模型每轮都能看到当前仍然生效的 skill。

但 active skill 也不是永久记忆。用户切换到无关任务时，模型应该调用 `skill_unload` 卸载不再相关的 skill，避免无关指令长期占用上下文。

### Runtime Context

Runtime context 和工作记忆一起进入 prompt，提供运行时事实：

- 当前本地时间。
- 当前日期。
- 时区。
- memory root。
- 当日 daily log 路径。

它主要服务长期记忆写入和 dream 整理。模型不需要猜日期，也不需要拼路径，可以直接根据 runtime context 找到当日日志文件。

## 4. 长期记忆

长期记忆是项目级跨会话信息，保存在项目对应的 memory 目录中。它不跟随单个 session 消失，也不会把所有历史都保存下来。

长期记忆分为三类：

```text
user_profile.md
feedback_workflow.md
project_context.md
```

### 用户画像

`user_profile.md` 记录用户稳定画像，包括：

- 用户身份和目标。
- 知识背景和技术水平。
- 表达偏好。
- 协作偏好。
- 希望面试中如何复述某些设计。

它不只是“用户偏好”，也包括用户背景。比如用户经常说“我基础比较缺乏，需要讲清楚”，这类信息会影响后续解释深度，就适合进入用户画像。

### 工作流反馈

`feedback_workflow.md` 记录用户对 agent 工作方式的稳定反馈，例如：

- 修改代码前要先讨论方案。
- 不要新增一堆小函数。
- 修改后要自己测试。
- 文档要写成总结笔记，不要写源码流水账。
- 工具输出不要展示太大块。

这类记忆不是项目业务事实，而是“agent 应该怎么和用户协作”。把它单独成类，可以让后续召回时更容易影响行为方式。

### 项目背景

`project_context.md` 记录项目级长期背景，例如：

- Codemate 是一个本地 coding agent。
- 目录结构迁移到了用户级项目状态目录。
- 权限系统包含审批和 bwrap 沙箱两层。
- 记忆系统采用 daily log + dream 整理。
- MCP 支持 stdio、streamable http 和 sse。

这些信息可能无法从当前代码快速看出来，或者属于用户和 agent 讨论后确定的设计方向，因此适合长期保存。

## 5. Daily Log

长期记忆不是由主 agent 每轮直接改三类长期文件，而是先追加 daily log。

Daily log 是原始记忆信号，格式固定：

```text
- [created_at] memory
```

例如：

```text
- [2026-07-08T14:23:10+08:00] User prefers code explanations that focus on design intent and execution flow.
```

Daily log 的特点是：

- append-only，只追加，不重写、不整理。
- 按日期存储。
- 记录“值得跨会话记住”的信息。
- 不作为最终长期记忆直接展示给主 agent。

这样设计的原因是：主 agent 在任务执行过程中判断“这条信息可能值得记住”比较容易，但要判断它该合并到哪一类、是否和旧记忆冲突、是否应该删除旧记忆，则更适合由 dream 统一整理。

## 6. Daily Log 写入规则

主 agent 的提示词要求：如果当前交互中出现值得跨会话记住的信息，需要在最终回答前追加到当日 daily log。

强信号包括：

- “remember”
- “from now on”
- “next time”
- “以后”
- “记住”
- “下次”

值得记录的内容主要是三类：

- 用户画像信号。
- 工作流反馈。
- 项目长期背景。

不应该记录：

- secret 或凭据。
- 一次性任务进度。
- 当前 todo。
- 原始工具输出。
- 临时调试噪声。
- 大段代码。
- 只在当前 turn 有用的信息。

另外 CLI 提供 `/remember <text>`，用于用户手动把一条信息追加到当日 daily log。这条命令适合记录明确的长期偏好或项目约束。

## 7. Dream 整理

Dream 是长期记忆整理流程。它读取 daily logs，把其中真正有长期价值的信息整理进三类长期记忆文件。

Dream 的职责不是继续完成用户任务，而是做 memory consolidation：

```text
daily_logs/*.md
  -> dream 整理
  -> user_profile.md
  -> feedback_workflow.md
  -> project_context.md
```

Dream 的提示词明确规定：

- 只处理 memory root 范围内的文件。
- 读取三个长期记忆文件和 recent daily logs。
- 只整理上次 cursor 之后的 daily log 条目。
- 不重写 daily logs。
- 长期记忆文件保持短 Markdown bullet list。
- 每条长期记忆必须是单行格式：`- [created_at] memory`。
- 冲突时按 created_at 保留较新的记忆。
- 重复或兼容记忆可以合并，使用最新 created_at。

这种设计让 daily log 成为原始缓冲区，dream 成为批处理整理器，长期记忆文件保持干净。

## 8. Dream 触发条件

Dream 支持手动和自动两种触发方式。

手动触发：

- `/dream`：前台执行，可以看到整理过程。
- `/dream --background`：后台执行，不阻塞当前交互。

自动触发：

- 距离上次 dream 至少新增 5 个 session。
- 距离上次 dream 至少 24 小时。

这两个条件同时满足时，主 agent 会启动后台 dream。这样可以避免 dream 太频繁，影响正常对话；也避免长期日志一直不整理。

Dream 状态记录在 `.dream_state.json` 中，主要包括：

- 上次 dream 时间。
- 上次 dream 时 session 数。
- 上次状态。
- 上次处理到的 daily log 文件和行号。

行号 cursor 很重要。Daily log 是 append-only 的，所以只需要记住“上次处理到哪个文件哪一行”，下次 dream 就能继续处理后续新增日志，不需要重新整理全部历史。

## 9. Dream 子 Agent

Dream 通过独立子 agent 执行，而不是让主 agent 直接改长期记忆文件。

子 agent 的运行特点：

- runtime mode 是 `dream`。
- 使用独立 session。
- 不继承主对话 history。
- 禁用长期记忆召回和自动 dream。
- 只允许 memory consolidation 需要的工具。
- `memory_scope_only` 限制它只能访问 memory root。

允许的工具包括：

- `list_files`
- `read_file`
- `grep`
- `write_file`
- `patch_file`
- `todo_write`

这样做的好处是把记忆整理和主任务隔离开。主 agent 不会被大量 daily log 和整理过程污染上下文；dream 也不会误读项目代码或改动非 memory 文件。

## 10. 长期记忆召回

长期记忆不会全部塞进 prompt。每次用户请求开始时，Codemate 会根据当前请求对三类长期记忆进行一次模型召回。

召回输入包括：

- 当前用户请求。
- 三类长期记忆文件内容。
- 三类记忆的语义说明。
- 召回规则和输出 schema。

召回输出是结构化结果：

```json
{
  "selected": [
    {
      "source": "user_profile",
      "text": "...",
      "reason": "..."
    }
  ]
}
```

召回结果会被限制：

- 最多 8 条。
- 单条 text 和 reason 都会截断。
- 只能选择长期记忆文件中明确存在的信息。
- 不能编造新记忆。

召回完成后，Context Manager 会按类别渲染：

```text
Relevant memory:
user_profile:
- ...
feedback_workflow:
- ...
project_context:
- ...
```

这样模型既能看到相关记忆，也能知道记忆来自哪个类别，减少误用。

## 11. 召回失败处理

长期记忆召回失败不会阻断主任务。

如果召回模型调用失败，runtime 会：

- 清空本轮 relevant memory。
- 标记 `long_term_memory_status = failed`。
- 在 trace 中记录失败事件。
- 继续执行用户请求。

这是一个重要设计：记忆是增强能力，不应该成为主任务的单点故障。即使记忆召回不可用，agent 仍然应该能正常读文件、改代码、回答问题。

## 12. 工作记忆与长期记忆的边界

工作记忆和长期记忆不能混在一起。

工作记忆适合保存：

- 当前任务目标。
- 最近读写文件。
- 文件短摘要。
- 工具失败提醒。
- 当前 todo。
- 当前 active skill。

长期记忆适合保存：

- 用户稳定画像。
- 用户对 agent 工作方式的稳定反馈。
- 项目长期目标、约束和架构决策。

不适合进入长期记忆的内容包括：

- “刚刚读取了某个文件”。
- “某条测试失败了一次”。
- “当前 todo 第二步未完成”。
- “某次工具输出的完整内容”。
- “一次性任务的中间状态”。

如果把这些临时信息长期化，后续召回会越来越脏，模型会被过期信息误导。

## 13. 与 Context Manager 的关系

记忆系统本身负责维护状态，Context Manager 负责把状态放进模型请求。

在 prompt 中，记忆相关内容分成两块：

- `Working memory`：当前任务状态，全部展示。
- `Relevant memory`：长期记忆召回结果，按类别展示。

Working memory 不通过模型召回，因为它本来就短，而且每条都和当前任务强相关。长期记忆可能越来越多，因此需要召回筛选，只把当前请求相关的部分放进 prompt。

这种分工可以避免两个问题：

- 工作记忆被召回算法漏掉，导致当前任务状态丢失。
- 长期记忆全部展示，占用过多上下文。

## 14. 与 History Compact 的关系

History compact 只压缩 history，不压缩 working memory 和 relevant memory。

原因是：

- working memory 是当前状态，不应该被混进旧对话摘要。
- relevant memory 是长期记忆召回结果，本来已经经过筛选。
- history compact 关注的是旧对话和旧工具观察的压缩。

不过两者互相配合。比如旧 `read_file` 结果可能在 history microcompact 中被清理，文件摘要则能在 working memory 中保留一个短提示；旧对话被压缩后，长期记忆仍能在下一次会话中召回稳定偏好和项目背景。

## 15. 设计难点

### 难点一：避免记忆职责重复

早期设计中，文件摘要和结构化笔记职责容易重叠。后来的设计把结构化笔记改成过程笔记，只记录工具错误和异常调用；文件摘要专注记录最近文件的轻量内容。

这样职责更清楚：

- 文件摘要回答“这个文件最近读到了什么”。
- 过程笔记回答“哪些工具调用刚失败过，不要重复踩坑”。

### 难点二：避免长期记忆变成垃圾桶

长期记忆最容易出的问题是越记越多、越记越杂。Codemate 没有让主 agent 直接频繁修改长期记忆文件，而是引入 daily log 作为缓冲层，再通过 dream 做批量整理、去重和冲突处理。

这个方案牺牲了一点实时性，但换来了更好的长期质量。

### 难点三：控制召回成本

关键词召回虽然快，但很容易漏掉语义相关信息，也容易召回无关片段。当前采用模型召回，准确性更高；为了控制成本，召回只在用户请求开始时运行一次，后续工具循环复用这一轮的召回结果。

后续工具循环不会反复召回，而是复用本轮结果。

### 难点四：防止后台整理影响主任务

Dream 如果直接复用主 agent history，会污染上下文，也可能误操作项目文件。因此它使用独立子 agent、独立 session、限制工具集合和 memory scope。

这样即使 dream 出错，也只影响记忆整理，不影响主任务执行。

## 16. 面试复述版本

Codemate 的记忆系统分成工作记忆和长期记忆。工作记忆是 session 内的短期状态，用来服务当前任务，包含任务摘要、最近文件、文件摘要、过程笔记、todo 和 active skills。它每轮都会进入 prompt，帮助模型减少重复探索、避免重复工具错误，并保持当前任务计划。

长期记忆是项目级跨会话信息，分为用户画像、工作流反馈和项目背景三类。主 agent 不直接频繁改长期记忆文件，而是在发现值得记住的信息时追加 daily log；后台 dream 再读取未处理日志，把稳定信息整理进三类长期记忆文件。这样 daily log 作为原始缓冲，dream 负责去重、分类和冲突处理。

请求开始时，Codemate 会对长期记忆做一次模型召回，只选和当前请求相关的少量条目，并按类别展示在 Relevant memory 中。召回失败不会阻断主任务。这样既能保留跨会话经验，又不会把所有长期记忆都塞进上下文。

整体设计的核心是按生命周期管理信息：当前任务状态放工作记忆，稳定跨会话信息放长期记忆，完整对话放 history，需要时再 compact。这样可以在长任务中维持连续性，同时避免记忆系统变成过期信息和工具输出的垃圾桶。
