## 1. 整体定位

Codemate 是一个面向本地代码仓库的 coding agent。它不是简单的聊天 CLI，也不是一次性调用大模型生成答案，而是一套围绕真实工作区构建的 agent runtime：能够理解用户请求、维护任务状态、组装上下文、调用工具读取和修改代码、执行验证命令、管理权限、记录运行过程，并在长任务中通过记忆和压缩机制保持连续性。

它希望支撑的是一个完整的本地编码闭环：

```text
理解任务 -> 规划步骤 -> 调查代码 -> 执行修改 -> 验证结果 -> 总结交付
```

这个闭环的关键在于，模型不只是输出文本，而是需要在真实环境里行动。它会读取文件、搜索代码、运行命令、写入补丁、调用网络搜索或 MCP 工具，也会遇到上下文过长、工具失败、权限风险、模型 API 格式不一致、会话恢复等问题。因此 Codemate 的重点不是某一个工具能力，而是把模型、工具、上下文、权限、记忆和终端交互组织成一个稳定、可控、可复盘的系统。

整体设计理念可以概括为：

- **模型负责决策，runtime 负责控制循环。** 模型决定下一步要做什么，runtime 保证工具调用、审批、记录、错误处理和最终收尾都按规则执行。
- **工具调用结构化。** 工具以 schema 的形式传给模型，模型返回标准 tool call，runtime 解析并执行，避免依赖 prompt 里模拟工具调用。
- **上下文分层管理。** 稳定规则、运行背景、长期记忆、历史对话和当前请求的生命周期不同，不能简单拼接后做滑动窗口。
- **权限系统和沙箱分层防护。** 审批系统负责判断能不能做，沙箱负责即使命令行为超出预期也不能越界。
- **长任务需要持续性。** 通过 Todo、Skill 历史注入、长期记忆、history compact 和旧工具结果清理，让 agent 能处理跨多轮、多文件、多工具调用的任务。
- **过程需要可见和可复盘。** commentary、工具结果摘要、trace、session/run 存储让用户知道 agent 正在做什么，也方便后续定位问题。

## 2. 整体架构 + 模块职责总览

Codemate 的整体架构可以理解为一条主链路：

```text
CLI / Terminal UI
    -> Model Client
    -> Runtime Loop
    -> Context Manager
    -> Tool System
    -> Memory / Storage / Trace
```

从用户视角看，用户在终端输入任务；agent 组装上下文并请求模型；模型返回中间进展、工具调用或最终回答；runtime 执行工具并把结果写回历史；如果任务未完成，就继续下一轮，直到完成或明确阻塞。

各模块职责可以概括为：

- **CLI/UI**：负责用户输入、slash command、工具结果展示、审批交互、会话恢复、模型和权限切换。它解决的是“agent 如何被舒服地使用”的问题。
- **Model Client**：负责兼容不同模型 API，把内部统一消息格式转换成 OpenAI 或 Anthropic 等 provider 的请求格式，再把响应转换回统一结构。它解决的是“多模型接口差异不污染 runtime”的问题。
- **Runtime Loop**：负责 agent 主循环，将用户请求推进成多轮模型请求和工具调用。它解决的是“模型如何持续行动直到任务完成”的问题。
- **Context Manager**：负责决定模型每轮能看到什么，包括 prefix、available skills、runtime context、relevant memory、history summary、recent history 和 current request。它解决的是“长任务上下文如何不丢重点也不爆掉”的问题。
- **Tool System**：负责真实世界操作，包括文件、搜索、shell、写入、todo、web、delegate、skill、MCP 等。它解决的是“模型意图如何安全可靠地落地”的问题。
- **Skill / MCP**：负责能力扩展。Skill 提供任务相关的专门知识和资源，MCP 接入外部工具服务。它解决的是“内置工具不够时如何扩展”的问题。
- **权限和沙箱**：负责审批策略、文件访问规则、shell 风险分类和 bwrap 沙箱。它解决的是“agent 能行动但不能失控”的问题。
- **记忆系统**：支持隔离的 Legacy Candidate/Dream 和 Progressive Core/Ordinary 后端，负责跨会话长期信息维护。当前任务状态由 history、Todo 和文件版本状态分别维护。
- **持久化层**：负责 session、run、task state 和 trace。它解决的是“会话如何恢复，行为如何复盘”的问题。

## 3. 具体模块设计

### 3.1 CLI/UI：终端交互和可见性

CLI/UI 是用户和 agent 交互的入口，负责启动 agent、读取用户输入、展示中间进展、显示工具调用结果、处理 slash commands、审批工具调用，以及切换模型、provider、approval 和 session。

它实现的核心能力包括：

- 交互式输入，支持方向键、历史输入和 slash command 补全。
- `/help`、`/session`、`/provider`、`/model`、`/approval`、`/remember`、`/dream`、`/compact`、`/budget` 等命令。
- 会话恢复和切换，支持查看会话列表、重命名、选择恢复。
- 工具调用和工具结果的可读展示。
- 审批交互，支持一次性允许、临时允许某个目录、拒绝等选项。
- banner 中展示 workspace、model、approval、session 等当前状态。

这个模块的设计核心是：coding agent 的可用性不只取决于模型能力，也取决于用户能不能看懂它在做什么。Agent 会频繁调用工具，如果终端里直接输出完整 JSON、长 stdout 或大量工具参数，用户很难判断任务是否在正确推进。因此 Codemate 对不同工具结果做了摘要展示：读文件、grep、网络搜索这类读工具只展示概要；shell 输出只保留 stdout/stderr 的前后几行；todo 和 delegate 用结构化格式展示计划和调查结果。

实现中遇到的主要问题是传统终端输入输出太弱。普通输入方式不支持方向键和命令补全，长工具输出会淹没真正有用的信息，审批选项如果靠手输数字也不够顺手。解决方式是把输入、输出、审批和摘要展示拆成 UI 层能力，让 runtime 只关心事件本身，不关心具体如何渲染。

### 3.2 Model Client 适配层：统一内部格式，兼容不同 API

Model Client 负责屏蔽不同模型接口的差异。Codemate 内部使用统一的消息和响应结构，runtime 只处理三类结果：

- **commentary**：用户可见的中间进展。
- **tool calls**：模型请求调用工具。
- **final answer**：任务完成后的最终回答。

具体请求模型时，再由 Model Client 转换为不同 provider 的格式。

OpenAI 和 Anthropic 的差异主要体现在：

- OpenAI Responses API 可以用 `phase=commentary` 和 `phase=final_answer` 表示不同可见输出阶段，也可以返回 function call。
- OpenAI Chat Completions 使用传统 `messages` 和 `tool_calls` 格式。
- Anthropic 使用 content blocks 表达 `text`、`tool_use`、`tool_result`。
- Anthropic 对 tool_use/tool_result 的配对顺序要求更严格，同一轮多个 tool_use 后必须紧跟对应 tool_result。
- 不同 provider 的 usage/token 统计字段也不一致。

因此 Codemate 的设计不是让 runtime 到处判断 provider 类型，而是在模型边界做适配：

```text
内部统一消息
    -> OpenAI input / Anthropic messages / Ollama messages
模型返回
    -> 统一 ModelResponse(commentary/tool_calls/final)
```

这样做的好处是 runtime loop、context manager 和 tool execution 都可以保持稳定，不需要感知不同 API 的细节。

这个模块遇到过一个典型问题：Anthropic-compatible 接口报错，原因是多个 tool_result 没有按照 Anthropic 要求合并到同一个紧跟 tool_use 的 user message 中。解决方式是内部 history 保持统一结构，但在 Anthropic 请求转换时，把连续 tool result 合并成符合协议的 content blocks，保证 API 消息合法。

### 3.3 Runtime Loop：Agent 的执行闭环

Runtime Loop 是整个 agent 的控制核心，负责把一次用户请求推进成完整的多轮执行过程。

整体流程可以概括为：

```text
接收用户请求
    -> 更新当前任务状态
    -> 构建上下文
    -> 请求模型
    -> 解析模型响应
       -> commentary：展示并写入 history，然后继续
       -> tool calls：校验、审批、执行工具、记录结果，然后继续
       -> final answer：展示最终回答，结束本轮任务
```

这个循环的关键是：模型不是一次性完成复杂 coding 任务，而是在不断观察和行动中推进。模型读取文件后会获得新信息，运行测试后会看到失败原因，执行修改后需要继续验证。因此 runtime 必须能稳定地处理“模型请求工具 -> 工具返回观察 -> 模型继续决策”的链路。

Runtime 还承担一些关键工程职责：

- 记录每轮模型请求、工具调用、工具结果和最终回答。
- 在工具调用前做参数校验和权限 gate。
- 处理工具失败、审批拒绝、重复调用等异常情况。
- 将工具错误写入工作记忆，提醒模型避免重复犯错。
- 在必要时触发 history compact 或长期记忆 dream。
- 保存 Todo、最近调用的 Skills、文件版本和临时权限等 session 状态。

这个模块的难点是模型行为具有不确定性。模型可能重复读同一个文件、完成任务后不收尾、工具调用参数错误、忘记运行验证，或者在 provider 格式转换上出问题。Codemate 的解决方式是把关键边界放到 runtime 和测试里，而不是完全依赖 prompt：重复调用拦截、工具 schema、权限 gate、task state、trace 和 history 结构校验共同保证执行过程可靠。

### 3.4 Context Manager：分层上下文、预算与压缩

Context Manager 负责决定模型每一轮“看到什么”。这是 coding agent 能否处理长任务的关键模块。

Codemate 将上下文分成几个层次：

```text
prefix
available skills
runtime context
relevant memory
history summary
recent history
current request
```

各层职责不同：

- **prefix**：稳定系统规则，包括工具使用、回答风格、进度说明、权限规则、工作流约束等。
- **available skills**：当前可用 skill 的名称和描述，帮助模型判断是否需要加载某个 skill。
- **runtime context**：少量运行背景，例如日期、时区和项目记忆目录。
- **relevant memory**：从长期记忆中召回的、和当前请求相关的信息。
- **history summary**：被压缩的旧历史摘要。
- **recent history**：最近未压缩的对话和工具交互。
- **current request**：当前用户请求。

这样分层的原因是：Prefix 需要保持稳定；长期记忆是跨会话事实；Todo 和 Skill 通过工具结果进入 history；history 是最容易膨胀的部分，需要专门压缩。

预算管理上，Codemate 使用模型上下文 token 上限作为总预算，并结合上一次模型 usage 和工具结果估算维护当前 token 使用情况。`/budget` 可以展示各部分字符数、工具 schema 字符数、估算 token、最大上下文和当前占比。这样做的目标不是精确到每个 tokenizer，而是给上下文增长提供可观察的指标。

History 处理是最复杂的部分。Codemate 不再只依赖滑动窗口，因为滑动窗口会丢掉旧决策、用户约束和已经解决的问题。现在采用两层策略：

1. **Microcompact 旧观察结果。** 较早的 read/search/web 类工具结果可能很长，而且随着文件变化会变得不可靠，因此只保留近期重要结果，旧结果替换为占位文本。为了避免关键信息丢失，prompt 要求模型在大型调查任务中及时把重要发现写进 commentary。
2. **History compact。** 当上下文接近预算上限时，fork 一个不使用工具的压缩子过程，将旧历史总结成结构化 summary，然后保留最近一段 history 继续工作。

这里遇到的难点包括：

- 工具结果很长，会迅速撑爆上下文。
- 旧 read_file 结果可能随着文件修改变得不可信。
- 如果只保留最近消息，会丢掉用户约束和历史决策。
- OpenAI 和 Anthropic 对 tool call / tool result 的消息结构要求不同，压缩和裁剪不能破坏工具配对。

解决思路是：工具结果可以清理，但关键发现必须沉淀到 commentary 或 summary；旧历史可以压缩，但最近工具交互必须保持结构完整。

### 3.5 Tool System：结构化工具和真实环境操作

工具系统负责把模型的意图转换成真实环境中的操作。每个工具都有 schema、description、参数校验、权限 gate、执行 handler、结果摘要和 trace 记录。

主要工具能力包括：

#### 文件调查工具

**list_files** 用于列出目录内容，帮助模型了解项目结构。它适合定位文件和目录，不适合读取具体内容。

**read_file** 用于读取指定文件。它支持读取目标路径，返回文件内容和行信息。对于已有文件的修改，Codemate 要求先 read_file 再 patch/write，避免模型在未读当前内容的情况下覆盖用户改动。

**grep** 用于搜索文件内容。它支持三种模式：

- `files_with_matches`：只返回包含匹配内容的文件，用于定位范围。
- `count`：返回每个文件的匹配次数和总数，用于评估影响规模。
- `content`：返回具体匹配行。

`content` 模式支持 `before`、`after`、`context` 获取上下文行，其中 `before/after` 优先级高于 `context`。这个设计借鉴了常见 grep/rg 工作流：先定位文件，再评估规模，最后读取具体内容。

#### 文件修改工具

**write_file** 用于创建、替换或追加文件。它支持 append 模式，适合追加日志或记录类文件。对于已存在文件，普通写入要求先读文件；append 可以作为普通追加能力使用。

**patch_file** 用于对已有文件做最小修改。它要求修改前读过同一个文件，并且文件 freshness 没有变化，避免基于过期内容打补丁。

这些规则的核心思想是保护用户工作区：agent 不能在没有读当前文件的情况下凭空修改，尤其是在 dirty worktree 中不能覆盖用户未提交改动。

#### Shell 工具

**run_shell** 用于执行命令。它能力强，但风险也最大，因此会经过 shell 风险分类、路径识别、审批策略和沙箱限制。它适合运行测试、语法检查、构建命令、只读调查命令等。

Shell 工具不会只依赖 prompt 约束，而是在执行前尽量识别命令类型和路径风险，在执行时用沙箱兜底。

#### Todo 工具

**todo_write** 用于复杂任务规划。它支持最多两层结构：phase 和 phase 内部 task。设计思路是渐进式展开：一开始可以只列粗粒度阶段，等调查到足够信息后，再把当前阶段细化成具体任务。

这样做是为了避免两种问题：

- 一开始不了解项目就列过细计划，容易错。
- 一直只列粗计划，长任务推进时容易混乱。

Todo 状态由模型维护，但工具会校验最多一个 phase in_progress、同一 phase 中最多一个 task in_progress，避免计划状态自相矛盾。`todo_list` 可以在计划不再位于最近上下文时按需读取完整状态。

#### 网络工具

**web_search** 用于搜索当前外部信息、官方文档、新闻或未知 URL。

**web_extract** 用于读取指定 URL 的网页内容，适合在搜索结果或用户给出链接后进一步提取正文。

**web_research** 用于更宽泛的多来源调研，适合用户明确要求 research 或需要综合多个来源的问题。

网络内容被视为不可信证据，而不是指令。Prompt 中要求模型不要执行网页里的指令，也不要把密钥、私有代码片段等敏感信息发送给 web 工具。

#### Delegate 工具

**delegate** 用于把边界清晰的只读调查任务交给子 agent。它可以同时执行多个调查任务，子 agent 不继承完整父 history，只拿到必要任务说明和只读工具能力。

Delegate 的价值不是替代主 agent，而是隔离上下文、减少主 agent 的探索噪声。主 agent 仍然负责最终判断、代码修改、验证和用户回答。

#### Review 工具

**review** 在修改形成可审查的整体后串行启动一个独立只读子 agent。它根据主 agent 提供的目标、约束和保留行为检查当前 Git 修改，并继续调查相关调用链、测试和项目惯例，避免修改者只从自己的实现视角验证代码。

Review 子 agent 不继承父 history，不修改文件，也不参与长期记忆维护；其 Markdown 报告返回主 agent，由主 agent判断 finding 是否成立并决定是否修复。

### 3.6 Skill 和 MCP：能力扩展机制

Skill 和 MCP 都是 Codemate 的扩展机制，但它们解决的问题不同。

#### Skill 生命周期

Skill 用于给 agent 加载任务相关的专门知识、工作流、脚本或模板。系统会先展示 available skills 的名称和描述，模型判断当前任务是否需要某个 skill，再调用 `skill_load` 加载。

加载后，工具结果返回 skill root 和完整正文并进入 history。Skill 下的 `scripts/`、`references/`、`examples/`、`templates/` 等资源都以该 root 为基准查找。

Session 保存最近调用的三个 Skill。Compact 后只恢复 recent history 中已经缺失的 Skill，不截断正文，也不在每次 prompt 中重复注入。

设计核心是：Skill 是按需加载的任务说明，通过 append-only history 保持缓存稳定，并由 compact 恢复保证长任务连续性。

#### MCP 动态工具接入

MCP 用于接入外部工具服务。Codemate 从配置中读取 MCP server，连接后调用 `tools/list` 发现工具，再把每个 MCP 工具包装成统一的内部 tool schema，注册到 tool registry。

当前支持三种连接方式：

- **stdio**：本地启动 MCP server 进程，通过标准输入输出通信。
- **streamable HTTP**：连接 HTTP MCP server，适合本地或远程 HTTP 服务。
- **legacy SSE**：兼容旧版 SSE MCP 服务。

MCP 工具接入后，模型看到的是普通 tool schema；runtime 执行时再根据包装信息找到对应 MCP server 和原始工具名，并调用 MCP client。这样 MCP 不会绕过 Codemate 的工具管理体系，仍然可以统一经过审批、trace 和结果展示。

MCP 的难点在于连接生命周期。最初每次调用都重新连接，会浪费资源，也容易出现异步上下文关闭错误。更合理的方式是启动时建立并保存连接，后续复用 session；如果断线，再重连一次。这样既不需要复杂的全生命周期管理，又避免每个工具调用都重新启动 server。

### 3.7 权限和沙箱：让 agent 能行动但不能失控

权限系统负责回答两个问题：

```text
这个工具调用是否允许？
如果允许，执行时如何防止越界？
```

Codemate 的审批策略包括：

- **ask**：默认策略。低风险读操作可以通过，写入和高风险操作通常询问用户。
- **auto**：自动模式。读类操作更宽松，部分工作区内写入可以自动通过，但危险命令仍需审批。
- **read_only**：只读模式。允许读取、搜索、todo、skill、web、delegate 等不修改工作区的能力，禁止写入类操作。
- **full**：完全信任模式，主要用于测试或明确放开权限的场景。

文件访问规则由 read/write allow/deny 组成。规则会聚合默认配置、用户配置、项目配置和 session 临时权限。deny 优先于 allow，避免敏感目录被误放行。审批时用户可以选择 allow once，也可以临时允许某个具体目录在本 session 中读或写。

Shell 是权限系统中最复杂的部分。Codemate 会先分析 shell 命令：

- **read**：只读命令，例如查看文件、列目录、部分检查命令。
- **risky**：普通修改命令，例如 mkdir、touch、cp、mv、重定向写入、pytest 等可能产生文件变化的命令。
- **unknown**：无法明确判断风险的命令。
- **dangerous**：危险命令，例如 rm、chmod、kill、reboot、python 脚本等可能执行任意逻辑的命令。

同时还会识别路径、重定向目标、通配符和危险目标。风险操作中出现通配符会直接拒绝，因为修改范围不可控。

但 shell 静态分析不可能完美。比如 `python test.py`、`eval`、脚本内部逻辑都可能绕过命令表面意图。因此 Codemate 引入 bwrap 沙箱作为第二层防护：

- 默认将文件系统大部分位置以只读方式挂载。
- read deny 的敏感路径用空目录覆盖或隐藏。
- write allow 的目录重新挂载为可写。
- shell 即使通过审批，也只能在沙箱允许的路径范围内产生写入。

这个设计的核心思想是：审批负责“用户是否同意执行”，沙箱负责“执行结果是否仍然被限制在授权边界内”。两者不冲突，而是互补。

### 3.8 记忆系统：状态分工和长期记忆

记忆系统解决的是 agent 的连续性问题。复杂 coding 任务往往跨越很多轮对话和工具调用，如果只依赖 history，信息会被工具结果淹没，也会在 compact 后丢失。

当前任务状态不再汇总成一个重复注入的 Working Memory。职责被拆分为：

- 当前任务和工具观察保存在 history。
- Todo 保存在结构化状态中，通过 `todo_write` 更新、`todo_list` 按需读取。
- Skill 正文由 `skill_load` 写入 history，compact 后按需恢复。
- 已读文件保存 `mtime_ns + size` 指纹，用于编辑前检测未读或外部变化，但不进入 prompt。
- 工具错误直接保留在 tool result，不再复制成过程笔记。

#### 长期记忆

长期记忆后端由 Session 固定选择，Legacy 与 Progressive 不会同时运行。Legacy
服务跨会话积累，分为三类：

- **用户画像**：用户身份、知识背景、偏好。
- **反馈与工作流**：用户对 agent 工作方式的反馈，例如不要乱改无关文件、修改 Python 后要 py_compile。
- **项目背景**：项目目标、约束、架构方向、重要决策。

Legacy 不是每轮直接重写，而是采用候选记忆 + dream 的方式。runtime 定期从完整对话中提取候选记忆；dream 后台任务定期读取未整理候选，把有价值的信息整理进长期记忆文件。

这样设计是为了降低长期记忆污染。如果每轮都让模型直接改长期记忆，容易把临时结论写成永久事实；如果完全不记，又无法跨会话保留稳定偏好和项目背景。候选记忆作为缓冲层，dream 作为整理层，可以在两者之间取得平衡。

Progressive 后端将用户明确表达的跨项目事实存入 Core，将项目决策、约束和问题经验按主题保存为 Ordinary Memory。每轮按访问频率和时间衰减选择 25 个标题，其他主题通过完整索引工具按需查找；达到增量阈值或 compact 前，由受限子 Agent 调查相关旧记忆并创建或更新主题。

### 3.9 持久化层：会话恢复和行为复盘

持久化层负责保存 session、run、task state 和 trace。

它实现的核心能力包括：

- 每个项目有独立的 session 存储。
- 每个 session 下保存对应 runs。
- session 可以命名、重命名、列出和恢复。
- run 中保存 task_state 和 trace。
- trace 记录模型请求、工具调用、审批、工具结果、错误和最终回答。

这个模块的核心价值是可恢复和可复盘。Coding agent 的问题经常不是一个函数局部错误，而是运行过程中的链路问题：模型看到的上下文不对、工具结果没有写入 history、审批状态恢复后不一致、MCP 工具没有加载、Anthropic 消息格式不合法等。只有保存 trace，才能回头分析每一步发生了什么。

会话恢复也是 coding agent 的重要能力。用户不一定一次完成一个大任务，因此 session 中需要保存 history、summary、todo、临时权限、记忆状态和标题。这样恢复后不仅能看到旧对话，还能保持 agent 当时的工作状态。

## 4. 当前阶段的整体评价

Codemate 目前已经具备一个本地 coding agent 的核心能力：

- 能通过结构化工具调用完成真实工作区操作。
- 能在多轮工具调用中维护上下文和任务状态。
- 能通过 commentary、todo 和 trace 提高长任务透明度。
- 能通过权限规则和沙箱控制文件与命令风险。
- 能通过长期记忆和 history compact 支撑跨轮、长上下文任务。
- 能通过多模型适配、Skill、MCP 和 delegate 扩展能力边界。

它的核心价值不在于某一个工具，而在于把模型、工具、上下文、权限、记忆、存储和 UI 组织成一个能持续工作的系统。这也是 coding agent 相比普通聊天助手最关键的工程复杂度所在。
